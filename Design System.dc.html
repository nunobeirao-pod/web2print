Web2Print UI Kit

The tokens and components that power the storefront and the design studio. Every value here is pulled from the live product — not invented — so this page and the site never drift apart. When a screen needs a new colour, spacing, or button style, add it here first, then reference it.

Developer Handoff

Building this into a real product

Every value on this page is the visual source of truth for the project. It was extracted directly from the live storefront and studio (not invented), and the 8 components below (Button, Link, Input, Select, Checkbox, Radio, Badge, IconButton) are the same components rendered on this page — not documentation-only mockups. When implementing in Next.js, port these tokens and component contracts 1:1; do not re-derive colours or spacing from screenshots.

Colours

Warm off-white base (#FBFAF8), near-black ink (#1C1B19), one brand blue (#4A4FE4) used only for actions/links/live status. Full palette incl. hover/disabled/tint variants in §1.

Typography

Single family: Helvetica Neue → Helvetica → Arial → system sans. 11-step scale from 52px Display to 10px micro-copy. See §2. User-authored canvas text in the Studio uses a separate ~14-font content palette — not a UI token.

Spacing

4px base scale: 4/8/12/16/24/32/48/64/80/96. Use these exclusively for margin/padding/gap — no arbitrary values. See §3.

Grid / Layout

Content max-width 1440px, centred. Horizontal padding 48px desktop / 32px tablet / 16px mobile (page padding — see §Tablet/Mobile detail for the distinction from section and component spacing). The Studio is a fixed 56px-toolbar + fluid canvas layout, not a content-width grid.

Responsive breakpoints

Desktop ≥1024px · Tablet 768–1023px · Mobile <768px. Full behaviour per breakpoint in §13.

Components

8 Core Components shipped: Button, Link, Input, Select, Checkbox, Radio (colour swatch), Badge, IconButton. These are Design System primitives — see System Architecture for how Product Patterns and Studio Patterns build on them. Full per-component contract in Component Specs below.

States

Every interactive component documents default/hover/focus/active/disabled. E-commerce components additionally document loading, empty, error, out-of-stock and selected — see §10.

Iconography

Line icons only, 1.7px stroke, round caps/joins, no fill. See §12.

New screens — Phase 2
404 — Page Not Found

Objective: tell the user the page doesn't exist and offer a way back. Components: Button, Link. States: single static state. Responsive: centred column, fluid font-size via clamp(), buttons wrap on narrow screens.

Order Confirmation

Objective: confirm a completed order. Structure: success icon, order ref, item list, subtotal/shipping/total, delivery address, payment method, next-steps note, actions. Components: Button, Link, image-slot. Note: address and payment method are placeholders — populated dynamically from the Medusa order object. Reuses: the same success pattern already live in Checkout.dc.html's isSuccess state (not altered) — this page is the fuller reference for the missing summary/address/payment fields; flagged for validation whether Checkout.dc.html should be updated to match. Responsive: single column, cards stack full-width below ~640px.

Password Recovery

Objective: let a user request a password reset. States: Initial, Validation (empty/invalid — reuses Fase 1 Input error pattern verbatim), Success, Error. Components: Input, Button, Link. Note: visual flow only — the reset mechanism itself is a backend concern. Responsive: single 420px column, centred, full-width below that.

Search Results

Objective: close the search flow: Search → Loading → Results → No results → Error. Structure: search input, term + count, filter chips, sort, product grid, pagination. Reuses verbatim: the Fase 1 Loading skeleton and No-results copy/markup (not altered), plus the Feedback error pattern. Components: Input, Link, product card, pagination pattern (§8). Responsive: grid reflows per §13; filters wrap under the heading on narrow screens.

Cookie Banner

Objective: cookie consent, neutral placeholder copy pending legal text. States: Default banner (Accept all / Reject / Manage preferences), expanded Preferences panel (Necessary locked-on, Analytics, Marketing toggles). Components: Button, Link, the existing toggle visual from §7 Forms. Responsive: banner switches from a row to a stacked column below ~640px (message above, actions below, full-width buttons).

Usage rules
  • Never hardcode a colour, radius or spacing value that already exists as a token above — reference the token.
  • One Primary button per view/section; destructive actions use the Warning/Error colour, never Primary styling.
  • Do not introduce new colours, radii or shadow values without adding them here first.
  • Keep the current visual design as-is — this handoff documents the existing site, it does not propose a redesign.

Implementation Handoff

Everything above (Tokens, Foundation, Core Components, Product Patterns, Studio Patterns) is technology-agnostic. This section is the one place technology is named — the intended build target is React / Next.js for the frontend and MedusaJS for commerce (products, cart, checkout, orders), but the Design System does not depend on either: a different stack could implement the exact same tokens and component contracts.

What belongs here
  • React/Next.js component structure, routing, data fetching
  • MedusaJS product/cart/checkout/order integration
  • API contracts, commerce logic, application state
  • Any framework-specific implementation notes
What does not belong here
  • Colours, type, spacing, radius, shadows (Layer 1)
  • Component visual contracts (Layer 3)
  • UX decisions already made in Product/Studio Patterns
AI implementation guidance

AI implementation must not redefine the Design System. The human-approved specification above is the source of truth.

AI may
  • Implement tokens/components in code
  • Generate already-specified variants
  • Detect inconsistencies and flag them
  • Help write/maintain documentation
AI may not
  • Invent new tokens or variants
  • Change UX decisions already made
  • Decide commerce/backend architecture
  • Mix backend logic into the Design System
  • Introduce a technology dependency into the Design System itself

System Architecture

The Design System is technology-agnostic: it defines visual language, interaction rules, accessibility and responsive behaviour independently of any framework or backend. It is not "a Design System for Next.js + Medusa" — those are one possible implementation of it (see Implementation Handoff). Nothing in this section changes any approved visual value — it only clarifies how the existing pieces relate.

Layer 1 — Design Tokens colour, type, spacing, radius, shadows, breakpoints (§1–6)
Layer 2 — Foundation / Accessibility focus, keyboard, tap targets, contrast, states
Layer 3 — Core Components Button, Link, Input, Select, Checkbox, Radio, Badge, IconButton (§Component Specs)
Layer 4 — Product Patterns Product Card, Cart Item, Checkout Summary, Product Gallery, Product Selector, Category Grid — built FROM Core Components, not primitives themselves
Layer 5 — Studio Patterns Studio toolbar, colour/outline pickers, panels — reuse tokens + Core Components, but are Studio-specific, not Design System primitives
Layer 6 — Implementation React / Next.js / Medusa / APIs / commerce logic — see Implementation Handoff, not part of the Design System itself
Primitive vs semantic tokens

Colours in §1 are listed by name and hex for clarity, but conceptually split into two roles. Today several semantic roles intentionally point to the same primitive value — that's a starting point, not a merge: each can be repointed independently later without touching every component.

Spacing: global vs component-specific

Global spacing tokens (§3): 4/8/12/16/24/32/48/64/80/96 — used for gaps, margins, section rhythm. Component-specific tokens exist where a component's own anatomy needs a value the global scale doesn't name directly — e.g. button.height (44px), input.height (~50px), header.height (56–68px). These aren't "arbitrary" — they're documented per component in §Component Specs, not hidden magic numbers.

13. Responsive Behaviour

Storefront pages are fluid with a 1440px content cap. The Studio is desktop-first — below a width threshold the inspector collapses from a fixed side panel into a toggled overlay.

Desktop (≥1024px)
Max-width 1440px, 48px side padding. Studio inspector pinned as a fixed 320px right panel; view switcher centred in the toolbar.
Tablet (768–1023px)
Side padding narrows to 24–32px. Product galleries and "you may also like" rows keep horizontal scroll instead of wrapping to a grid.
Mobile (<768px)
Nav links collapse into a menu; Studio inspector becomes a bottom-toggled overlay (narrow state) with a floating tools button in the toolbar.
Mobile detail — Phase 3A reference frame 390px, verified to 320px
Grid & container
16px side padding (vs 48px desktop). Multi-column desktop grids (4/5-up carousels, category rails) collapse to 2 columns. Content is always minmax(0,1fr) — never a fixed px width.
Spacing & typography
Same 4px scale and type sizes as desktop — no separate mobile scale. Section spacing tightens to the lower end of the scale (16–32px) instead of 48–96px.
Navigation
The flat desktop link row is replaced by a hamburger IconButton opening a full-screen overlay menu (top-level items 44px+ tap rows, in-place accordion for sub-links). Full spec: Mobile Navigation.dc.html.
Drawers (Cart / Login)
Already responsive as built — both use width:460px;max-width:100vw, so they naturally become full-width sheets on mobile with no code change. Verified in Cart Mobile.dc.html.
Touch targets
Button ≥44px, size chips 44×44px, Radio/Swatch has a 44×44px invisible hit-area (Phase 1.1) around its unchanged visual size. Open gap: IconButton is 36×36px, below the 44px guideline — not resized here (would change desktop toolbars); flagged for a decision.
Screens already mobile-ready
404, Order Confirmation, Password Recovery, Search Results and Cookie Banner (Phase 2) were built single-column/fluid and verified at 390px as-is — no separate mobile file was created for these, per the reuse rule.
Tablet detail — Phase 3B.1 base/infrastructure only — no Tablet pages built yet

Tablet fills the gap the Desktop/Mobile breakpoints already implied (Desktop ≥1024px, Mobile <768px) — so Tablet = 768–1023px, verified at 768 / 834 / 1024. No existing rule was overridden to get this range.

Container & gutters
Fluid, no max-width needed below the 1440px Desktop cap. Side padding 32px (the value already named for Tablet in this section) — between Desktop's 48px and Mobile's 16–20px.
Grid
Grids that run 4-up on Desktop and 2-up on Mobile (product/category grids) run 3-up on Tablet. Grids that already scroll horizontally on both Desktop and Mobile (Trending, category-tile rows) keep scrolling — no new pattern.
Header / Navigation
Keeps the Desktop inline nav, not the Mobile hamburger — the nav already uses gap:clamp(10px,1.1vw,18px) with no fixed widths, so it compresses instead of overflowing down to 768px. The hamburger pattern stays a <768px-only rule, as already documented.
Spacing
Section padding drops one or two steps on the existing 4px scale — Desktop's 96/64px sections use 48–64px on Tablet — never a new, off-scale value.
Media & typography
Both already fluid (aspect-ratio images, clamp() headings) and need no Tablet-specific override — they were already safe at this width before this phase.
Components & overflow
Same components, same states (loading/empty/error/disabled/validation/payment-refused) — no Tablet variants. Standing rule from the Phase 3A.4 fix: never a fixed-px container width — always width:100%;max-width:<value>, so nothing overflows between 768–1024px.
